## 内容摘要

文章从 Pi 根目录的构建脚本出发，说明一个 coding agent 如何通过九个包和分层依赖组织起来。Pi 的主干可以概括为产品层 `pi-coding-agent`、运行时层 `pi-agent-core` 和模型层 `pi-ai`；终端 UI、RPC、会话存储和遥测等能力作为支撑。CLI 的 interactive、print 和 rpc 三种运行模式共享同一个 `AgentSession` 核心，差异主要位于输入输出层。

## 主要内容

### 1. 构建顺序体现依赖图

文章给出的构建顺序是：

`tui → telemetry → ai → agent → session-backends → protocol → client → server → coding-agent`

被依赖的包先构建，产品层最后构建。文章将这种严格的单向依赖视为 Pi 能够拆分和复用的基础。

### 2. 三层主干和支撑能力

- 产品层：`pi-coding-agent`，包含 `pi` 命令、三种运行模式、内置工具、扩展系统和会话持久化。
- 运行时层：`pi-agent-core`，负责 agent 主循环、工具调度、会话状态和上下文压缩；模型、文件系统和 shell 都通过可替换接口接入。
- 模型层：`pi-ai`，提供统一的多模型服务商 SDK，入口可以脱离产品层单独使用。
- 支撑能力：`pi-tui` 负责终端 UI；`protocol`、`client`、`server` 组成 CBOR RPC；`session-backends/sqlite-node` 负责 SQLite 会话存储；`pi-telemetry` 提供遥测契约；文章还提到 `pi-evals` 评估框架。

### 3. 三种运行模式

- `interactive`：终端是 TTY 时的默认模式，提供完整 TUI。
- `print`：通过 `--print` 或管道输入执行单次请求，适合脚本。
- `rpc`：通过 stdin/stdout 使用 JSONL 协议，供其他程序嵌入或远程驱动。

三种模式共享 `AgentSession`，会话状态、上下文压缩、模型管理和持久化保持一致。

### 4. 一次请求的执行路径

用户在 TUI 中输入内容后，`AgentSession` 追加会话消息并调用 `runAgentLoop`。主循环组装上下文，通过 `pi-ai` 的 `Models.stream()` 找到服务商适配器并发起请求。模型流式返回的 delta 被转成统一事件，再传递到 TUI。

如果模型需要使用工具，主循环会在 `message_end` 后执行工具，把结果写回上下文并发起下一轮请求。消息、模型切换和工具结果会以 JSONL 追加到 `~/.pi/agent/sessions/` 下的会话文件；文章将这个文件描述为可分叉的事件树，而不是单纯的流水账。

### 5. 工程和供应链约束

文章还提到 Pi 可以脱离 Node 编译成 Bun 单文件原生二进制，直接依赖使用精确版本，依赖包需要满足 `min-release-age=2`，发布的 CLI 通过 shrinkwrap 固定传递依赖。作者把这些约束视为一个默认拥有用户全部权限的工具应具备的基本供应链安全措施。

## 文章中的观点

- 构建顺序就是理解项目架构的低成本入口。
- Pi 的可拆分性和可嵌入性来自依赖方向、接口替换和共享核心，而不是表面上的包数量。
- 对高权限 coding agent 来说，依赖版本和发布延迟约束属于用户信任的一部分。
