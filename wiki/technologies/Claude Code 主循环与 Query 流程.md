# Claude Code 主循环与 Query 流程

## 摘要

Query Loop 是 coding agent 的执行心脏：接收用户消息，调用模型，判断是否需要工具，执行工具，将结果写回上下文，再继续或结束。专栏文章进一步将 Claude Code 的调用拆为 `ask → QueryEngine.submitMessage → query → queryLoop`，并把流式事件、跨轮状态、协议修复和输出截断恢复视为生产级主循环的关键。

## 核心内容

### 四层调用

- `ask`：面向 SDK/脚本的一次性入口。
- `QueryEngine.submitMessage`：处理本轮会话状态、消息历史、系统提示和工具集合。
- `query`：用异步生成器包装并向外转发执行事件。
- `queryLoop`：执行“准备上下文 → 调模型 → 判断 → 执行工具 → 回写结果”的循环。

通过 `yield*`，最内层产生的模型增量、工具事件和状态更新可以一路传到终端或其他调用方，实现边执行边显示。

### 正常路径与异常路径

正常路径是模型决定调用工具，运行时执行并把 `tool_result` 加入下一轮；没有待执行工具时生成最终回答。真实系统还要处理用户中断、工具崩溃、上下文过长、循环不收敛、输出超长和 API 协议不完整。

文章描述一种协议修复：如果工具调用没有对应结果，构造带有调用 ID 的错误 `tool_result`，让下一次 API 请求保持结构完整，同时把失败事实交回模型。输出被截断时，则先重试或提高输出上限，必要时要求模型从断点续写。

### 状态边界

跨轮信息不能依赖全局变量。会话消息、文件缓存、权限拒绝、子任务状态和压缩信息应放在明确的状态对象中，由主循环统一读写；这样取消、重试和异步子任务才有可追踪的恢复点。

## 我的理解

Agent 主循环的质量主要体现在异常路径，而不是 `while` 本身。实现时应先定义事件协议、状态边界和可恢复错误，再设计模型调用；每次工具调用都应有明确的开始、结果、失败、取消和超时状态，避免一次孤立消息把整个会话卡死。
