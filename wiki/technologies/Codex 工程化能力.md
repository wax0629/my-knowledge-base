# Codex 工程化能力

## 摘要

一篇关于 Codex 工程化能力的文章把项目级 Agent 工作拆成五类机制：`AGENTS.md` 管固定规则，Skills 管按需加载的专项流程，Subagents 管独立上下文和并行分工，MCP 管外部系统连接，Hooks 管生命周期自动检查。这个划分有助于把规则、知识、分工、连接和自动化放到不同边界中。

## 核心内容

### 五类机制的职责

| 机制 | 主要职责 | 适合承载的内容 |
| --- | --- | --- |
| `AGENTS.md` | 持续约束项目行为 | 目录约定、格式规范、修改边界、检查命令 |
| Skills | 按需加载专项能力 | 发布、迁移、评审等可复用流程和参考资料 |
| Subagents | 拆分独立任务和上下文 | 并行调研、代码探索、测试和问题归类 |
| MCP | 连接仓库外部系统 | 云文档、Issue、数据库和协作工具 |
| Hooks | 自动触发生命周期动作 | 测试、格式化、安全扫描和结果记录 |

### AGENTS.md：规则层

文章把 `AGENTS.md` 比作项目入职手册。规则应具体到目录、文件格式、可修改范围和验证命令，避免只写“注意质量”这类无法检验的要求。

文章描述的规则加载模型是从项目根目录向当前目录逐层合并，越靠近当前目录的规则优先级越高；同一层的 `AGENTS.override.md` 优先于 `AGENTS.md`。这些细节属于文章对 Codex 的产品说明，当前版本是否完全一致需要独立核对。

### Skills：知识和流程层

不是每个任务都需要的长流程适合放入 Skill，而不是全部塞入 `AGENTS.md`。Skill 的核心文件是 `SKILL.md`，可以附带参考资料、脚本、模板和其他资源。文章强调渐进式加载：先根据名称和描述判断匹配，再按需读取完整流程及其资源。

### Subagents：分工层

主 Agent 可以把相互独立的调查或实现任务分派给独立上下文，再统一收集、去重和合并结果。这样可以减少中间过程对主上下文的占用。

Subagent 的上下文隔离与 Worktree 的文件隔离是两件事：前者解决任务分工和信息组织，后者解决多个任务并行修改文件时的冲突。若多个 Subagent 同时改同一批文件，仍需要显式协调。

### MCP：外部连接层

MCP（Model Context Protocol）为 Agent 连接外部系统提供统一的工具发现和调用方式。文章用 Host、Client、Server 解释调用链，并区分 Tools、Resources 和 Prompts 三类能力。

MCP 能扩大 Agent 获取信息和执行操作的范围，同时也扩大权限、认证和外部副作用的风险。实际接入时需要明确哪些操作只读、哪些操作会写入外部系统，并对授权范围进行检查。

### Hooks：自动化层

Hooks 把固定动作绑定到任务生命周期节点，减少依赖提示词重复提醒的流程。文章列举的节点包括 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse` 和 `Stop`。

一个典型流程是：任务准备结束时运行检查脚本；通过则结束，失败则把摘要返回给 Agent 继续处理。Hook 的价值在于固定触发时机和可重复验证，但具体事件名称、Handler 协议和失败行为必须以当前实现为准。

## 与已有知识的关系

本条目补充了 [[Agent 运行时与多入口模式]]：后者关注 Agent 核心运行时如何适配不同 I/O 入口，本条目关注项目规则、专项能力、任务分工、外部连接和生命周期控制等运行时周边的工程化机制。

它也与 [[Pi coding agent 架构]] 形成互补：Pi 条目记录一个 coding agent 的产品层、运行时层和模型层如何组织，本条目记录使用或扩展 coding agent 时如何组织项目协作能力。两者不应合并为同一个架构主题。

## 我的理解

这五类机制可以按稳定性和触发频率分层：每次任务都必须遵守的规则放在 `AGENTS.md`；只有特定任务需要的长流程放在 Skills；可拆分的工作交给 Subagents；仓库外的信息通过 MCP 获取；固定的验证动作交给 Hooks。

这个分工减少了单个提示词承担全部项目知识和流程的压力，也让“应该怎么做”和“如何证明做完了”分别落到规则、流程和自动检查上。它是从文章案例提炼出的工程方法，不意味着所有 Agent 产品都使用相同的目录或配置接口。
