# OpenClaw 本地自主 Agent

## 摘要

OpenClaw 在本专栏中被描述为运行在个人设备上的本地自主 Agent：它把大模型、工具、设备节点、消息通道、技能和长期记忆组合成一个可以持续工作的执行系统。这个案例适合用来观察“聊天模型如何变成有身体、有状态、有权限边界的 Agent”，但其中的当前实现细节仍需独立核验。

## 核心内容

### 组件地图

文章描述的主要角色如下：

- Gateway：负责身份鉴权、会话状态和请求路由。
- Agent：调用模型、拆解任务、协调工具并推进执行。
- Tools：单项能力，例如读写本地文件、发消息或调用软件接口。
- Skills：把多个工具组合成可复用的工作流程。
- Channels：把飞书、微信、Telegram 等外部消息转换成统一输入输出。
- Nodes：运行在手机、电脑等设备上的节点，为 Agent 提供摄像头、位置、屏幕或系统控制能力。

### 记忆与工作空间

文章把工作空间和记忆设计成可读的 Markdown 文件，再配合轻量索引。短期信息来自按天记录的会话日志；长期信息被提炼到 `MEMORY.md` 一类文件中。文章进一步描述用 SQLite 的向量搜索扩展与 BM25 做混合召回，让人可以直接修改文本而不必手工维护索引。

### 与普通 Agent 的差异

文章强调四个差异：长期常驻、主动执行、接入真实设备和消息平台、跨会话保留偏好与事实。它的价值不只在模型回答质量，而在于把“感知、决策、行动、记忆和通信”连成可持续运行的闭环。

### 与云端常驻 Bot 的对照

另一篇产品报道把 Grok Bot 描述为拥有专属云端计算机、可以后台运行并通过浏览器界面操作网站的多 Bot 系统。相较之下，本条目记录的 OpenClaw 路线强调本地优先、消息通道、设备节点和可切换模型。这个对照说明“常驻 Agent”可以有本地设备型和云端托管型两种实现，但不代表两者当前版本的产品边界已经独立确认。

### 风险与成本

本地高权限意味着更大的误操作、隐私泄露和命令执行风险。持续心跳、多轮工具试错、记忆抽取/召回以及每次请求携带的规则和工具描述都会增加 Token 成本。文章建议把权限、设备能力、可执行工具和人工确认边界显式化。

## 我的理解

本地自主 Agent 的核心不是“把聊天窗口搬到电脑上”，而是同时解决执行权限、持续运行、状态持久化、外部连接和失败恢复。评估这类系统时，应把“能做什么”与“默认允许做什么”分开记录；可检索的 Markdown 也只有在写入质量、召回策略和验证机制都可靠时才构成真正记忆。
