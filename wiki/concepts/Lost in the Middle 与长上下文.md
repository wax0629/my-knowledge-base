# Lost in the Middle 与长上下文

## 摘要

`Lost in the Middle` 指语言模型处理长上下文时，相关信息放在开头或结尾通常比放在中间更容易被正确检索和使用的现象。它不是注意力公式规定的“中间不可见”，而是模型在长序列中的位置偏差、信息竞争、上下文编码方式和训练分布共同产生的性能退化。

## 核心内容

### 现象是什么

典型测试把同一条“答案信息”在一组干扰文档中的位置不断移动：

```text
[问题/指令] + [干扰项] + [答案所在文档] + [干扰项] + [生成答案]
```

只改变答案文档的位置，不改变问题和答案本身，模型准确率常呈首尾高、中间低的 U 形曲线。论文在多文档问答和合成 key-value 检索中都观察到了这个趋势。

### 从注意力公式看为什么会发生

单个注意力头可以简化为：

```text
alpha_i = softmax(score(query, key_i))
output = sum(alpha_i * value_i)
```

模型理论上可以给任意位置较高分，但实际使用时会出现几层问题：

1. **竞争与信噪比下降**：上下文变长后，更多干扰 token 参与 softmax 竞争。如果目标信息没有明显高于干扰项，分配给它的有效权重会变小，后续层接收到的信号更容易被噪声淹没。这能解释“长”为什么更难，但不能单独解释所有中间位置偏差。
2. **decoder-only 的因果遮罩**：在常见的“文档在前、问题在后”布局中，文档 token 的隐藏状态不能看到未来的问题。最终问题 token 可以回看文档，但中间文档并没有先按当前问题完成 query-aware contextualization；把问题放在文档前后会改善这一点。论文发现它对 key-value 检索帮助很大，但对需要理解和综合的多文档问答帮助有限。
3. **首尾位置先验**：上下文开头经常承载系统指令、任务格式或标题，结尾靠近最新问题和输出位置。预训练与指令数据会让模型学习到首部的任务锚点和尾部的近期信息，中间内容没有同样的边界优势，于是出现 primacy/recency bias。
4. **位置与长度分布失配**：模型可能在较短序列上训练，再通过扩展窗口或位置编码变换处理更长序列。位置表示和注意力模式在训练分布之外未必稳定。论文观察到 encoder-decoder 模型在训练长度内较稳健，超过训练长度后也出现 U 形退化。
5. **多层信息路由失败**：最终答案不是从一个 token 直接复制，而是多个头、多个层共同把证据写入残差流并转化为输出概率。中间证据只要在若干层中没有被选中或被干扰，后续层就可能无法恢复。这是对 Transformer 信息流的机制性解释，不是论文证明的单一因果结论。

### 关键边界

- 这是“可访问但不稳健使用”，不是“中间 token 不能被 attention 看到”。
- 它不等于简单的“越远越差”：首尾通常比中间更好，位置和上下文长度共同决定结果。
- 它也不只由指令微调造成。论文在基础模型和随机化干扰项顺序的实验中仍观察到类似趋势。
- 注意力热力图不能直接当作因果解释；需要同时分析位置编码、因果遮罩、残差流、MLP、头的功能和最终任务输出。

## 与已有知识的关系

[[Claude Code 上下文窗口管理]] 关注如何通过落盘、裁剪、压缩和恢复减少无效上下文；本条目解释即使上下文没有超出窗口，模型也可能无法均匀利用其中的信息。[[RAG 检索与评估]] 中的精排、上下文组装和来源标记，可以用来降低把关键证据埋在中间的风险。[[Agent 基础概念与协议]] 则提供把检索结果交给模型并继续行动的更大执行框架。

## 我的理解

长上下文的有效容量不等于标称窗口大小。工程上应把“能装下”与“能找准、能综合、能验证”分开测试。对高价值证据，可以通过检索和精排减少干扰，使用结构化摘要或分块处理，并在评测中随机改变证据位置，报告最佳与最差位置的差距，而不是只测一种固定模板。

## 待核实

- 不同新模型、不同位置编码和不同上下文训练方法的偏差程度需要逐模型评测。
- softmax 稀释、位置先验和多层路由分别贡献多少，不能只用原论文的行为实验裁决。
- RAG、重排、查询前后重复和摘要策略可能缓解位置偏差，但也可能增加 token 成本或引入重复信息，需要在具体任务上测量。
