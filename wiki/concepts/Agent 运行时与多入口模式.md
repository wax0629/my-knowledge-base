# Agent 运行时与多入口模式

## 摘要

多入口 Agent 的一种架构方式是把会话状态、模型管理、上下文压缩、工具调度和持久化集中在一个运行时核心，再为终端交互、脚本调用和 RPC 嵌入提供不同的 I/O 外壳。Pi 的 `AgentSession`、`interactive`、`print` 和 `rpc` 是这一模式的具体案例。

## 核心内容

### 核心与入口分离

核心运行时负责可复用的状态和行为：

- 会话消息和持久化
- 上下文组装与压缩
- 模型选择和流式调用
- 工具调度及工具结果回写
- 统一事件分发

入口层负责适配不同的输入输出环境：

- 交互式入口适合人在终端中持续对话。
- print 入口适合管道和自动化脚本的一次性调用。
- RPC 入口适合被其他程序远程驱动或嵌入。

### 请求处理模型

一个请求可以抽象为：

`入口输入 → 会话追加 → Agent 主循环 → 模型流式事件 → 工具执行（可选）→ 上下文回写 → 下一轮或入口输出`

只要三种入口都经过同一主循环，核心行为就不会因为入口不同而出现三套实现逐渐偏离的问题。入口差异被限制在协议、显示和进程连接方式上。

### 设计收益

- 一致性：交互式使用、脚本调用和远程调用共享状态语义。
- 可测试性：运行时可以脱离终端 UI，用更简单的输入输出驱动测试。
- 可嵌入性：服务端或其他应用可以直接调用核心，而不必携带完整终端界面。
- 可替换性：模型、文件系统和 shell 等外部能力通过接口接入，运行时不绑定单一环境。

## 与已有知识的关系

本条目是从 [[Pi coding agent 架构]] 中抽取的通用架构概念。Pi 提供了具体命名和请求链路，但本条目中的设计收益是基于该案例的归纳，不等同于所有 coding agent 都必须采用的方案。

## 我的理解

多入口的重点不是提供更多命令，而是确保入口变化不会复制核心逻辑。设计时可以先确定稳定的会话和事件模型，再把终端、脚本、RPC 等表面形式作为适配器接入。

这类拆分对权限边界也有帮助：运行时可以明确声明需要哪些工具和外部能力，入口层只负责传输和呈现。不过权限隔离是否真正成立，仍取决于具体实现，不能仅凭分层名称判断。
